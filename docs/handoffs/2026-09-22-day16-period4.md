## 책임 경계와 설계

- 게임 서버가 기록한 `event_time`을 Spark timestamp로 바꿔 창 기준으로 사용한다. `published_at`이나 Spark 처리 시각으로 대체하지 않는다.
- `raw_value`와 Kafka topic·partition·offset을 parsing 단계에 보존한다.
- schema version 1이며 event ID와 event time이 있고 허용된 세 행동인 레코드만 창 입력으로 사용한다.
- 10초 watermark와 겹치지 않는 10초 tumbling 창을 event type별로 계산한다.
- 결과는 `data/lake/windows/tumbling`, checkpoint는 `data/checkpoints/windows/tumbling`에 둔다.
- 최근 완료 micro-batch의 전체 공개 progress JSON은 `data/marts/progress-windows-tumbling.json`에 둔다.
- 새 `batchId`가 확인될 때만 같은 폴더의 `.tmp` 파일을 완성한 뒤 최종 progress 파일로 교체한다.
- 터미널에는 `batchId`, `numInputRows`, `eventTime`, `stateOperators`만 출력하고 누락 필드를 임의 숫자로 만들지 않는다.
- `한번에_실행.md`에 NiFi를 제외한 Kafka 3개·Spark Master·Worker 1 실행, Django·publisher·변환기·창 query·접속기 순서를 추가했다.
- Windows Hadoop sink가 없는 중첩 폴더를 만들 때 실패하지 않도록 두 목적지 폴더를 query 시작 전에 생성한다.
- 출력 `count`는 고유 사건 수가 아니라 해당 창·행동의 전달 레코드 수다.
- 3교시 범위에서는 tumbling만 실행한다. `sliding`은 명령 계약에 보이지만 Spark 작업이 명시적으로 거부하며 6교시에서 구현할 자리다.
- 교안 예시의 `PROJECT_DIR/game_server/spark_jobs`는 현재 폴더 구조에 없으므로 실제 경로인 `PROJECT_DIR/spark_jobs`를 사용한다.

## 검사와 남은 관찰

사용자 요청에 따라 Spark 메모리 상한도 함께 낮췄다. 최초 1GB 구성 후 Kafka 안정성을 위해 16일차 경량 프로필을 추가로 적용했다.

- 16일차 실행 Worker: Worker 1만 사용, 2 core·768MB
- Spark Master·Worker daemon: 프로세스당 192MB
- 시간 창 Spark driver: 768MB
- 시간 창 Spark executor: 768MB·총 2 core
- `spark-defaults.conf`: driver·executor 768MB, core·기본 partition 상한 2
- 기존 다른 Spark 관리 명령: 명시한 최대 1GB 유지, 16일차에는 실행하지 않음
- Kafka: 기존 노드당 `-Xms128m -Xmx384m` 유지

`start-dev.cmd -Service day16`은 Kafka 3개, Spark Master와 Worker 1만 별도 창으로 열며 Docker/NiFi preflight도 실행하지 않는다. Docker Desktop을 종료한 상태에서도 이 프로필을 사용할 수 있다. 외부 Spark 설치 폴더는 Git 저장소가 아니다.

16일차 검증 도중 Docker NiFi·ZooKeeper 6개가 WSL2의 `VmmemWSL`에서 약 3.9GB를 사용하고 있었다. 16일차 1~4교시에는 NiFi가 필요하지 않아 `docker compose stop`으로 컨테이너만 중지하고 Docker Desktop과 WSL VM도 종료했다. Compose 볼륨과 NiFi Flow는 삭제하지 않았다.

초기 1GB 실행 검증에서는 Spark Master와 Worker 2개를 임시로 시작했다. Master 로그에서 두 Worker가 각각 `1 cores, 1024.0 MiB RAM`으로 등록됐고, 시간 창 application의 executor 실행 명령도 각각 `-Xmx1024M`을 사용했다. `game_windows.py`는 streaming schema, `event_time` 10초 watermark, tumbling query, Parquet 출력과 독립 checkpoint 경로까지 정상 초기화했다.

검증 당시 Kafka의 `127.0.0.1:9092`, `9094`, `9096`이 모두 꺼져 있어 입력 레코드를 읽지 못했다. 따라서 `data/lake/windows/tumbling`에는 Spark metadata만 생겼으며 실제 Parquet 결과 행은 아직 확인하지 않았다. 빈 결과를 성공한 집계로 기록하지 않는다. Kafka를 시작한 뒤 아래 `run_game_windows` 명령을 다시 실행해야 첫 창 결과를 확인할 수 있다.

검증을 위해 시작한 Spark query, Worker 2개와 Master는 모두 종료했다. NiFi·ZooKeeper도 중지 상태이며 볼륨은 유지했다. 마지막 포트 확인에서 `4040`, `7077~7079`, `8080~8082`, `8443~8445`에 listener가 없었고 `VmmemWSL`도 종료 상태였다.

최종 경량 설정에서는 Spark Master와 Worker 1만 임시 실행했다. Worker는 `2 cores, 768.0 MiB RAM`으로 등록됐고 시간 창 executor는 `-Xmx768M`과 2코어로 실행됐다. 유휴 Java 작업 집합은 Master 약 199MB, Worker 약 203MB였으며 확인 직후 query→Worker→Master 순서로 종료했다.

`C:/MLO01-01/Chapter3/Oder-insight/Spark-exam`의 Spark 설치본 세 개 가운데 실행기와 `server/.env`가 참조하는 것은 `spark-4.1.3-bin-hadoop3-1` 하나다. `-2`, `-3` 설치본은 실행 프로세스가 없어 RAM을 사용하지 않으며 디스크만 사용한다. Docker Compose에는 Spark 서비스가 없고, Docker 메모리는 NiFi·ZooKeeper 컨테이너가 사용했다.

확인한 실제 게임 사건의 시각 예시는 다음과 같다. `event_time`은 게임 서버 확정 시각이고 `published_at`은 이후 Kafka 전달 시각이다.

```text
event_id: aef7ec84-400d-406c-856b-edc5cb953d1a
event_time: 2026-09-21T05:48:28.725556+00:00
published_at: 2026-09-21T05:48:29.028754+00:00
```

실행한 검사:

```powershell
.\.venv\Scripts\python.exe -m py_compile ..\spark_jobs\game_windows.py analytics\management\commands\run_game_windows.py
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py help run_game_windows
& 'C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe' -NoProfile -ExecutionPolicy Bypass -File '.\tools\start-dev.ps1' -Service day16 -CheckOnly
```

Python compile, Django system check, `run_game_windows` 및 사용자 추가 `publish_window_demo` 관리 명령 help와 PowerShell 구문 검사는 모두 통과했다. `start-dev.ps1 -Service day16 -CheckOnly`은 Kafka·Spark 파일과 선택 포트를 확인하고 Docker/NiFi 검사를 건너뛰었으며 서비스는 시작하지 않았다. 실제 실행 검증에서도 Worker 1개가 2코어·768MB로 등록되고 executor가 768MB·2코어로 시작되는 것을 확인했다. 마지막 확인에서 관련 포트가 모두 닫혀 있고 `VmmemWSL`도 종료 상태였다.

새 계정 생성, 기존 Player 초기화, 더미 Topic 발행은 이번 범위에 포함하지 않는다.
