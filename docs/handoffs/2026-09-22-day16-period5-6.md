## 책임 경계와 설계

- `--kind tumbling`은 10초 길이·10초 이동 간격, `--kind sliding`은 20초 길이·10초 이동 간격을 사용한다.
- 두 종류 모두 서버 `event_time`과 10초 watermark를 사용한다.
- 결과·checkpoint·progress·Spark query name·Kafka group prefix를 `kind`별로 분리한다.
- 출력 `kind`는 고정 문자열이 아니라 실제 실행 인자에서 만든다.
- Spark가 첫 배치에 직접 만들어야 하는 `checkpoint/state`는 미리 만들지 않는다.
- Windows에서 Spark 배포판에 이미 포함된 `slf4j-api` 중복 전달이 멈추지 않도록 `--exclude-packages org.slf4j:slf4j-api`를 제출 인자에 추가했다. Kafka connector package는 유지한다.
- 게임 상태, Django 모델, 인증, 운영 WebSocket 계약은 변경하지 않았다.

## 5교시 실행 결과

`game.actions.window-demo.v1`을 partition 1, replication factor 3, `min.insync.replicas=2`로 만들고 phase 1~5를 순서대로 한 번씩 발행했다. 최종 offset은 7이다.

별도 `data-window-demo` 루트에서 tumbling query를 실행했고 최종 watermark는 `2026-09-11T01:00:55.000Z`였다. 확정 결과는 다음 네 행이다.

```text
[10:00:00, 10:00:10) player.moved count=2
[10:00:10, 10:00:20) player.moved count=2
[10:00:20, 10:00:30) player.moved count=1
[10:00:40, 10:00:50) player.moved count=1
```

기준 시각 +65초 사건은 최종 watermark보다 뒤의 열린 창에 있어 아직 출력되지 않는 것이 정상이다.

## 6교시 실행 결과

- Kafka 시작/끝 위치: partition 0=`598`, 1=`35`, 2=`261`
- 첫 배치 입력: 894행
- watermark: `2026-09-21T05:39:57.387Z`
- watermark로 닫혀 Parquet에 기록된 sliding 집계: 175행
- distinct `kind`: `sliding` 한 종류
- 최종 상태: 새 입력을 기다리는 idle 상태 확인 후 query 종료

샘플에는 같은 사건 시각대가 `[17:07:20,17:07:40)`와 `[17:07:30,17:07:50)` 두 20초 창에 들어가 10초 slide가 적용된 것을 확인했다.

검증 과정에서 계정이 다른 Driver와 Worker가 만든 실패 metadata가 있어 해당 폴더를 `data/lake/windows/sliding-failed-20260922`로 보존 이동했다. 이 폴더는 성공 결과에 포함되지 않는다. 자동 승인 검토가 재귀 삭제를 데이터 손실 위험으로 거절했으므로 삭제하지 않았다. 광범위한 ACL 변경도 적용하지 않았다.
