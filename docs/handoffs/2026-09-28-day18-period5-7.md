## 설계 결정과 책임 경계

- `collect_game_metrics`는 Kafka metadata와 committed offset만 읽는다. subscribe/poll/commit을 하지 않는다.
- `generated_at`은 관리명령의 관찰 시각이며 `spark_progress.timestamp`는 기존 Spark driver 기록 시각이다.
- `load_snapshot`은 `by_player`를 방별 연결·성공 수로 축약하고 계정별 행과 environment를 응답에서 제외한다.
- 두 HTTP view는 저장된 작은 JSON만 읽는다. 부하 측정, publisher, Kafka consumer, Spark 작업을 실행하지 않는다.
- `run-50`은 요청 50명, 연결 성공/peak 48명, 오류 2건이었다. 요청 수와 관찰값을 같은 값으로 바꾸지 않았다.

## 라우팅 문서 정합화

이동한 관리명령, 변경한 분석 view·URL·비교 도구와 새 테스트 파일의 1:1 문서를 현재 시그니처·파라미터·의사코드·직접 호출·값 출처에 맞췄다. 서버 색인에서 작성 중 보조 모듈 항목을 제거하고 정식 Django 관리명령 항목으로 이동했다.

## 실행하지 못한 검사와 남은 위험

- 새 비밀번호 입력이 필요한 부하 측정은 다시 실행하지 않았다. 저장된 동일 조건의 완료 결과를 사용했다.
- 마지막 120초 관찰 구간에는 새 게임 행동이 없어 `confirmed_count=0`이다. 파일 미생성 상태와 달리 실제 120초 구간의 측정값이다.
- `login_required` API의 실제 브라우저 로그인은 자동화하지 않았고 RequestFactory 계약 테스트로 인증·미생성·허용 응답을 검증했다.
- 최종 확인 시 Spark application UI 포트 4040은 이미 실행 중인 사용자 작업이 사용하고 있었다. 이번 작업에서는 해당 장기 실행 프로세스를 시작하거나 종료하지 않았다.
